# Game Pals — project context

All-in-one casual games app (board, card, party, puzzle, reflex) for **every surface**: iPhone, iPad, Mac (iPad app on Apple silicon + PWA), Android phones, tablets and Chromebooks, Windows/Linux (PWA), web and game portals. Surfaces, modes and the test matrix: `docs/13-platforms-and-testing.md`. Every game must fit portrait and landscape, work with touch, mouse and keyboard, and pass e2e on all 8 Playwright screen types.
Every game supports as many of these as make sense: solo, vs bot (Easy/Medium/Hard/Expert), same-device 2–4 players, online random, online friends/family, async turn-based. Everything except online works offline.

Read `README.md` and `docs/` first — decisions are recorded there. Update the relevant doc when a decision changes. Full build plan: `docs/08-roadmap.md` + `docs/04-tech-architecture.md`.

## Locked decisions
- **Phaser 4 + TypeScript + Vite**, Preact for menus/shell, **Capacitor** for iOS/Android. Developed fully in the cloud (GitHub Codespaces); builds on GitHub Actions (web, Android) and Codemagic (iOS). Nothing heavy installed on the owner's Mac.
- **Zero budget:** free tools/tiers only. Apple + Google developer accounts already exist.
- Game rules live in `packages/rules`: pure, deterministic TypeScript (seeded `createRng`, no `Math.random`, no Phaser/DOM imports). Client, bots, tests and the server referee all use it.
- Backend: Cloudflare Workers + Durable Objects + D1 (free tier), Firebase Auth/Messaging/Analytics/Crashlytics. All online calls go through our own `IBackend` interface.
- Ads: `@capacitor-community/admob` (MIT), rewarded-first. Purchases: RevenueCat. Portal builds (CrazyGames/Poki) use portal SDKs instead of AdMob.
- App saves: native storage (`@capacitor/preferences` / SQLite), never localStorage/IndexedDB inside the apps (iOS can evict them). Use `storage` from `apps/client/src/platform.ts` (Preferences in the apps, localStorage on the web), never `localStorage` directly. `platform.ts` also provides device haptics and the Android Back button (game → table → home).
- **Slow bots think in a Web Worker:** `apps/client/src/bot/worker.ts` + `bot/runner.ts`, for the games in `HEAVY_BOTS` (deep search or playouts). Only the move log crosses over; `chooseBotMove` (`packages/rules/src/games/catalog.ts`) rebuilds the game there, keeping the last few games so each move costs one apply, not a full replay. Quick bots decide inline from the live state, because a message round trip costs more than their thinking. Both paths seed from the game seed + move number, so they agree. If a worker cannot start, errors, or passes an 8 s budget, the move is worked out on the main thread.
- **Keyboard play is required:** every game plays with keys too, via `games/keys.ts` (`onKeys`, `focusRing`, `moveRing`): number keys where they fit, arrows + Enter/Space, a grape focus ring that hides on touch.
- **Installable web app (PWA):** `vite-plugin-pwa` precaches the whole build so the web app installs and opens offline. The service worker is registered in `main.tsx` on the web only, never inside the native apps or self-test builds. App icons come from `apps/client/scripts/make-icons.mjs` (`pnpm --filter @gamepals/client icons`).
- **Build flags:** `VITE_SELFTEST=1` for the native self-test builds, `VITE_PORTAL=1` for the game-portal build (no service worker, since a portal serves from its own origin; CI asserts it and keeps the `portal-build` artifact).
- **Test mode:** `?autoplay` (web) or `VITE_SELFTEST=1` builds (native) put bots in every seat and speed games up; `e2e/full.spec.ts` (@full) and the native jobs use it to play every game to the end.
- No GPL code in shipped apps (e.g. no Stockfish). No trademarked game names (see docs/03). CC0/permissive assets only, logged in `docs/licenses.md`.
- No free-text chat — emotes/preset phrases only. Bots never cheat.
- Look & feel follows `docs/12-catalog-and-direction.md` Part 3 (supersedes the style in docs/11): white app, flat candy colors from `apps/client/src/theme.ts`, **no gradients**, cute bubbly rounded UI, original vector art (`components/Art.tsx`), crisp rendering (`games/crisp.ts` — every scene calls `fitCamera` first), springy/physical motion (gravity, arcs, squash), and choices made by tapping things (table setup), never forms. Every action gets motion + `cue()` sound/haptic. Run the per-game juice checklist before calling a game done.
- Game catalog and build waves: `docs/12-catalog-and-direction.md` Part 2.
- **Bright** candy colors (not pastel). Every game has a plain-language `howTo` (goal, controls, win, draw/tip) shown before play. All app text is simple and plain spoken, and never uses em dashes.
- **Teach and keep score:** the first time a game is opened, one line under the board says what to do first (`firstplay.ts`, `tryIt` in the registry, defaulting to the first sentence of `howTo.controls`); it goes on the first move or after ten seconds and never takes a tap. Games between the same players keep a running score on the device (`rivalry.ts`), shown on the result sheet and the table, and following a player's **name** rather than their seat, because seats rotate between games.
- **Facing:** use `facing()` / `isPerson()` from `apps/client/src/games/duel.ts`. With two people, the top player's text is flipped; against a bot, all text faces the person and the bot's controls/hints are hidden.
- Audit of every game against its real rules: `docs/games/audit.md`.
- **SVG in Preact:** write SVG attributes in dashed form (`stroke-width`, `text-anchor`, `dominant-baseline`, `font-size`). Preact v10 passes camelCase SVG props through unchanged, and the browser ignores them. Center text with `text-anchor="middle"` + `dominant-baseline="central"` on each `<text>`.
- **One look, the flat one** (docs/12 Part 3). A second look was built behind `?look=2` over a day (a dark card room, then a bright Playrix-style playroom with gradients, lips and shadows) and dropped: the owner did not like it. Do not reintroduce a second look without being asked.
- **Nothing that is keyed on changing text may animate from `opacity: 0`.** `.turn-pill` did, and in a game whose line changes every move it never became visible at all. Entry animations for live text start part-way up (`pill-in`).
- **Pro is sold three ways with lifetime as the hero.** Monthly, yearly and lifetime, and the page leads with lifetime because that is what this audience buys (JindoBlu's Remove Ads at $6.99 against 413K ratings; Ponder Club's ad-free forever). Ads are rewarded-first with a hard cap on interstitials and never inside a turn, because ad frequency is the loudest complaint in every review set we read. The web app is a real channel too: Ponder Club is not in the App Store at all.
- **Green CI is not a picture.** Tests say a game runs and finishes; they cannot say it looks right. Card-game seat names shipped twice running off the table and sitting on the piles, then three word games in a row printed a status line through their own content, then Go Fish ran four seat names into each other with nothing overlapping anything. Download the `gallery-iphone` artifact from the run and look at the new game before calling it done, and turn whatever you find into a check the scene can answer. The gallery waits for the scene's tweens to settle before it shoots, because a shot at a fixed moment catches whatever was mid-flight and a domino halfway from a chip to the table looks exactly like a domino drawn on a player's name; judging a moving frame is guessing (`labelCheck()`, `handCheck()`, `tileCheck()`, `fanCheck()`, `boardCheck()`, `activeCheck()`).
  **The gallery waiting on tweens is not enough on its own:** a scene that moves things in `update()` rather than by tweening (Four in a Row's falling disc, every real-time game) looks settled to it, and the canvas can be a frame behind the HTML status line, so a picture can show a caption that contradicts its own board. Both are Q4 in the roadmap.
  **Prove the check red before you fix anything.** Twice this project has shipped a check that could not fail: one compared a scene to itself, one measured nothing at all. A check pushed on its own that comes back red, naming the number it saw, is worth the CI run every time; it also tells you when your diagnosis is wrong, which is how the Colour Sort tubes turned out to be a squash yoyo rather than the entry pop everything pointed at.
  **And a check that samples has to sample where the thing happens.** The Yatzy shout check polled the scene every 250ms and went green on both engines while the banner was provably sitting on the dice: the overlap lasts a few hundred milliseconds and the shout lingers for over a second, so the poll saw plenty of shouts and almost never a guilty one, and the "did it see anything" guard was satisfied entirely by the innocent samples. Moved inside the scene and recorded at the instant of the shout, it failed at once. A green from a sampling check is only worth what its worst-case window is. **A scene with a status line owes a `layoutCheck()`**: it returns the horizontal bands it draws in, and `e2e/wordlayout.spec.ts` fails when any two overlap. Placing a line at a computed `y` without reserving a band for it is the mistake that keeps happening.
- **Ask it of the rules before you ask it of a browser.** Nineteen games carry an invariant saying what can never happen to them: cards and tiles and seeds are conserved, a disc never hangs in Four in a Row, Chess always has both kings, a Sudoku given never changes, a Sliding Puzzle stays solvable after every slide. These are pure functions, so `scripts/precheck.sh` runs them on the spot for nothing, and a wrong answer names the number it saw. Five of the nineteen were wrong on first write and every one was found in seconds, where the same misreadings arriving through a gallery screenshot cost an hour each and twice pointed at the wrong fix. A browser is the right instrument only for questions that are really about drawing; everything else belongs in `packages/rules`, where it is free.
- **A test that plays whole games says how long it needs.** In the rules tests that is `it(name, { timeout: 120_000 }, …)` (vitest); in e2e it is `test.setTimeout(300_000)` **inside** the test, because Playwright's third argument takes no `timeout` and typecheck fails if you pass one. Reaching for the vitest form in a spec costs a run. CI runners are slower and busier than a laptop, and two of these have tripped the 5s default at 5030ms and 5103ms, failing a docs-only push. If a new test simulates games, give it a timeout.
- **`legalMoves` must list everything `apply` accepts**, unless the state answers `allows(move)`: a pool shot is a direction and a power, millions of them, so Pool is the first game where `allows` is the authority and `legalMoves` is a spread for bots and tests. (It was going to be `accepts`, until CI showed FreeCell already has a private `accepts` meaning something else; with a matching signature the helpers would have quietly started trusting it. Grep the games before naming an optional method on the contract.) Look moves up with `moveFor` / `isLegalMove` (`packages/rules/src/core/moves.ts`) wherever one arrives from outside. Otherwise: `replay` (`packages/rules/src/core/replay.ts`) is the server referee and validates every move against `legalMoves`, so a list narrower than what the rules really take means a person makes a perfectly ordinary move and the server then refuses to verify their game. Four word games had this: Word Guess listed only answers while accepting any real word, the crossword listed only the right letter when typing wrong ones is the game, Word Search listed a line one way round, Word Groups listed only the right four. Where a bot wants a shorter list, give it its own method (`candidates()`, `right()`), never narrow `legalMoves`.
- **Research before building:** every game gets a brief in `docs/games/<id>.md` (real rules with sources, what makes it feel right, reference apps, our design, tests) before any code. Each game must be clearly its own game, not a reskin of another.
- **CI minutes:** the repo is public now (seen 2026-09-23: runs bill 0 minutes), so Actions is free. It was private with 3,000 minutes a month, which ran out on 2026-09-18, and that is why a push runs two engines (`desktop-chrome` + `iphone`), the full eight only at a milestone end, and the Android emulator and iOS are opt-in. Those limits stay until the owner says otherwise. Details in `docs/08-roadmap.md`.
- **Nothing ships unless it's green:** one CI pipeline (`.github/workflows/ci.yml`): typecheck + unit tests + build → Playwright e2e on a phone browser (every game opened and played; any console error fails) → deploy web. Phone builds (TestFlight / Play internal) go out on release tags `v*` through the same gate. Add every new game to `apps/client/e2e/smoke.spec.ts`.

## Layout
- `packages/rules/src/core` — `GameDefinition`/`GameState` contract, `createRng`, negamax search, `createSearchBot`, move-log `replay`.
- `packages/rules/src/games/<id>` — one folder per game (rules + bot tiers + tests).
- `apps/client/src/session.ts` — runs any mix of human/bot seats; scenes only render `session.state` and call `session.play`.
- `apps/client/src/games/<id>` — Phaser scene per game; register it in `apps/client/src/games/registry.ts`.

## Commands
- `pnpm dev` — client on port 5173 (open the forwarded port on a phone)
- `pnpm test` — Vitest (rules)
- `pnpm typecheck`, `pnpm build`
- `scripts/precheck.sh [test paths]` — the checks that run on a machine with no `node_modules` (the owner's Mac): duplicate rules exports, duplicate art functions or tile keys, imports nothing uses, names the client imports from `@gamepals/rules` that the barrel never exports, every game present in all six test lists, and the rules tests through a small vitest stand-in. Run it before pushing; CI has caught each of these at least once. It cannot see unused locals or parameters, which typecheck fails on; `scripts/unused-scan.sh <files>` catches most of them, **including in test files**, where an unused helper has failed CI.

## Adding a game
1. `packages/rules/src/games/<id>/index.ts`: immutable state class, `GameDefinition`, bot tiers as data; export from `packages/rules/src/index.ts`.
2. Tests: legal moves, win/draw, illegal moves throw, replay, bot tier ordering.
3. `apps/client/src/games/<id>/<Name>Scene.ts` + registry entry.
